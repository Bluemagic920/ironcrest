# Company announcements

Owners save private drafts, edit drafts, explicitly publish notices to employees with active company access, and archive notices. Published notices are read-only; corrections use archive and a replacement draft. Archives are retained in owner history and hidden from the employee feed. There are no hard deletes, automatic posts, emails, push notifications, attachments or read receipts. This feature does not pull data from employee profiles, attendance or payroll.

Owner GET/POST `/api/announcements`; employee GET `/api/employee/announcements`. Posting is owner-only. Authentication is verified with Supabase, and the current sole active role membership determines organization. Owner access also requires organization ownership. Both require current Business entitlement and the existing rate limiter. Caller-supplied organization/user identifiers are rejected. Employee reads are restricted to published rows in their verified company, with a second check on returned scope/state. Metadata responses omit organization and author identifiers.

The service-only `ironcrest_announcement_action` function uses SECURITY INVOKER, rechecks owner and Business access, locks existing notices, and compares revisions. Publication and archiving retain timestamps. Concurrent or stale edits fail without overwriting another change. New table RLS is enabled; ordinary clients receive no direct table or function grants. `docs/announcements-schema.sql` is the reviewed snapshot of hosted migration `ironcrest_company_announcements`. The release gate is `ENABLE_COMPANY_ANNOUNCEMENTS=true`.

Lists use 25-notice pages. Owner filters include drafts/published/archived. Keyset cursors preserve exact timestamp precision and UUID tie breaks; values are validated before building scoped provider queries. Employees cannot request draft/history filters. Dates use Company Settings time zone. Message bodies are plain text, allow line breaks, and are rendered with textContent; markup is never executed.

The browser scrolls panels into view, clears company notices on account changes, fences delayed replies, and requires reload after attempted writes before another change. Publishing must be an explicit action on a saved draft. Preview and hosted tests use invented messages; hosted transactions roll back so no verification notices are committed to the live company feed.

Validation covers actual Worker integration, employee/company isolation, draft/history rejection, exact-precision pagination, plain-text rendering, authentication/rate-limit/redirect failures, competing edits in independent local PostgreSQL sessions, and draft/publish/archive transactions. It also preserves the existing Employee Profiles, Scheduling, Company Settings and read-only Attendance checks.
