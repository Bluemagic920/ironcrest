# Scheduling

Owners create assigned draft shifts, edit drafts, publish them, and retain cancellations. Employees can read only their own previously published shifts and cancellations. Draft cancellations are not visible to employees. Published shifts cannot be edited or reassigned: cancel and create a replacement. There are no hard deletes, email notifications, recurring shifts, availability requests, shift swaps, or payroll calculations in this release.

Company Settings supplies the time zone and first day of the workweek. Schedule inputs and date filters use that company zone, independently of the browser zone. The browser converts local input to explicit UTC instants. Nonexistent and ambiguous daylight-saving input times are rejected with a message. Existing attendance reports remain UTC. A draft save is rejected if the company zone changed since loading the editor. Shifts may cross midnight but must be future shifts of no more than 24 hours.

Owner routes: GET `/api/scheduling/context`, GET `/api/scheduling/shifts?start=...&end=...`, POST `/api/scheduling/action`. Employee routes: GET `/api/my-schedule/context` and GET `/api/my-schedule/shifts?...`. The shift window is half-open and bounded; UI allows 31 company calendar days, list limit200 with truncation disclosure. Picker choices are limited to200 active employees/worksites and disclose truncation. Names only are exposed; no phone, email, GPS or profile employment fields.

`worker/scheduling.mjs` is an extension, not the full existing Worker. It requires `ENABLE_SCHEDULING=true`, existing fixed-project bindings, verified confirmed authentication, exactly one active role membership, server-derived organization, Business entitlement, and the existing rate limiter. Owner creation must also match `organization.created_by`. Personal lists enforce self identity and published visibility in the query and reject foreign or draft rows. Only the service credential can access the table/RPC; no public-client grants or RLS policies are introduced.

`docs/scheduling-schema.sql` is the reviewed snapshot of the hosted migration `ironcrest_protected_scheduling`. The security-invoker, service-only RPC rechecks owner/Business and locks the organization to serialize mutations, including publication overlap checks. It rechecks active employee and active same-company worksite at save and publication. Revision checks prevent lost updates; overlapping published shifts for one employee cannot both publish, while adjacent shifts can. Cancellation retains history and the original `published_at` visibility boundary. Permission revocation blocks subsequent actions. Scheduling does not change attendance records or attendance release flags.

After any attempted mutation, the UI requires a reload before another action. It never retries a potentially committed draft automatically. Changing accounts clears records, picker names, editor state and date filters; late replies cannot restore them. Only explicit form submission or a named action button performs a write.

Validation: production scripts exercised in fixture DOM/network tests, actual full Worker integration checks, isolated PostgreSQL tests including independent concurrent sessions, and a hosted rollback-only transaction covering draft/publish/overlap/revision/cancellation. Browser sample preview verified draft editing, publication, retained cancellation and time-zone display using invented data. Release still needs explicit approval to enable the new employee schedule access, followed by live authenticated reads. No real schedule rows were retained during testing.
